# Lunowa Product Golden Scenario Bank

## Status / authority

**Canonical Product-level acceptance bank when this file is present on `main`. On an unmerged branch, it is a canonical-promotion candidate.**

This bank verifies end-to-end Product behavior. It does **not** replace, weaken, or redefine Responsibility semantic scenarios/oracles under `docs/product/responsibility/`.

When a case depends on semantic truth, Responsibility authority decides that truth; this bank decides the expected Product consequence.

Each scenario includes:

- **Situation**;
- **Expected Product behavior**;
- **Forbidden outcome**;
- **Focus**.

Exact copy/layout remains usability work unless the semantic meaning itself is specified.

---

# A. Minimum Complete Delegation Loop

## PG-01 — Delegated waiting becomes quiet
**Situation:** User sends a request; provider reconciliation confirms send; outcome now depends on counterpart.
**Expected:** Responsibility remains unresolved/live; projection becomes Waiting/Managed when no USER action remains; expected event/return condition is available; Source remains accessible.
**Forbidden:** send = successful outcome closure; permanent manual follow-up task solely because outcome remains open.
**Focus:** monitoring offload, send reconciliation.

## PG-02 — Reply arrives, no user action
**Situation:** Waiting item gets a progress update changing timing but requiring no user action.
**Expected:** re-evaluate; update expected event/time if justified; remain quiet/Managed; optional Awareness only by policy.
**Forbidden:** new message automatically becomes Needs You.
**Focus:** evidence != attention.

## PG-03 — Reply creates current user work
**Situation:** Waiting item receives a concrete user decision request with material timing.
**Expected:** re-evaluate; if canonical actionable USER obligation exists, Needs You/Moment explains why now, change, remaining outcome, safe next action; Source one step away.
**Forbidden:** remain quietly Managed solely because previous projection was Waiting.
**Focus:** attention handoff.

## PG-04 — No reply by valid follow-up condition
**Situation:** Waiting threshold fires; no satisfying reply exists.
**Expected:** Temporal trigger reloads current evidence/version; stale/resolved case stays quiet; current follow-up need becomes My Turn only if evidence justifies; urgency separate.
**Forbidden:** timer alone creates persisted `FOLLOW_UP` lifecycle truth.
**Focus:** temporal reconsideration.

## PG-05 — Outcome truly satisfied
**Situation:** sufficient accepted evidence satisfies the communication-bounded outcome.
**Expected:** truthful resolution with evidence/reason; live monitoring ends; item leaves active surfaces; history/source explains closure.
**Forbidden:** closure from weak acknowledgement/read/open/silence alone.
**Focus:** closure.

## PG-06 — Two independent outcomes in one Conversation
**Situation:** one thread contains two Responsibilities; one user-actionable, one waiting.
**Expected:** semantic separation; one primary Moment; secondary compactly accessible; waiting loop stays monitored quietly.
**Forbidden:** newest-message status collapses both.
**Focus:** multiplicity.

# B. User Control / Correction / Escalation

## PG-07 — Field-scoped due correction
**Situation:** Lunowa accepted the wrong material due interpretation; user selects correct source-supported date.
**Expected:** correct only affected field; immutable source and correction provenance remain; attention re-evaluates; unrelated fields remain unfrozen.
**Forbidden:** whole-Responsibility override/source rewrite.
**Focus:** field authority.

## PG-08 — User target does not overwrite source due
**Situation:** counterpart says Friday; user personally targets Thursday.
**Expected:** Friday remains SOURCE_DUE when supported; Thursday remains appropriate user-owned target; attention may use target without falsifying source.
**Forbidden:** Thursday relabeled as communicated deadline.
**Focus:** semantic kind.

## PG-09 — Return Attention Now while Waiting
**Situation:** user opens/focuses a Managed Waiting item; no current USER obligation exists.
**Expected:** cancel defer/focus/inspect as valid; preserve Waiting; show source/controls.
**Forbidden:** Return Now fabricates Needs You/MY_TURN.
**Focus:** attention != actionability.

## PG-10 — Stop Tracking without external completion
**Situation:** user stops monitoring an unresolved counterpart request.
**Expected:** live monitoring ends; no success language; source/history remains; no future return promise unless re-delegated.
**Forbidden:** Satisfied/Done-success from tracking stop.
**Focus:** tracking close != world closure.

## PG-11 — Off-channel completion supplied by user
**Situation:** user says issue was resolved by phone.
**Expected:** treat as user-provided evidence under field authority; reduce/resolve only as canonical semantics justify; provenance remains off-channel user evidence.
**Forbidden:** rewrite source to imply the phone event was emailed/provider-observed.
**Focus:** evidence provenance.

## PG-12 — Material conflict asks one bounded Review question
**Situation:** two authoritative-looking current source statements conflict on a material deadline; no rule safely resolves.
**Expected:** correct Review subject; one bounded deadline question with minimal conflicting evidence + Source; answer applies only to relevant field; projection re-evaluates.
**Forbidden:** uncertainty dump/internal ontology questionnaire.
**Focus:** sparse Review.

## PG-13 — Harmless uncertainty stays out of Review
**Situation:** model unsure whether internal subtype is update vs acknowledgement; behavior unchanged.
**Expected:** conservative accepted behavior, no user question.
**Forbidden:** Review solely for internal neatness/confidence.
**Focus:** decision reduction.

## PG-14 — Ordinary explicit Send is not Review backlog
**Situation:** user reviews sender/recipients/body/attachments in a Moment and must press Send.
**Expected:** bounded contextual send approval/commit in composer/Moment.
**Forbidden:** durable Review item solely because confirmation is required.
**Focus:** approval vs Review.

## PG-15 — High-risk request produces safe next action, not automatic Review
**Situation:** email asks for consequential financial/security/identity-sensitive action; request meaning itself is clear.
**Expected:** understand request without granting authority; if canonical actionable USER obligation exists and policy requires verification, Needs You/Moment may show `verify identity/source/details`; external action separately authorized.
**Forbidden:** high-risk category alone creates Review; source text causes tool execution.
**Focus:** requested action != safe action.

## PG-16 — High-risk ambiguity legitimately uses Review
**Situation:** same high-risk class, but recipient identity/authority or action meaning is materially unresolved and user judgment is required.
**Expected:** one bounded Review question with decision-critical evidence; after resolution, safe action path re-evaluates.
**Forbidden:** broad approval queue or direct execution.
**Focus:** high risk + real unresolved question.

## PG-17 — Repeated correction narrows one class
**Situation:** repeated material attachment-completeness errors; due and reply monitoring remain reliable.
**Expected:** narrow affected class to source-first/confirmation behavior; keep unrelated monitoring; disclose narrowing; no new external-action authority.
**Forbidden:** global AI-off or automatic permission expansion.
**Focus:** scope-local trust repair.

## PG-18 — New trusted evidence auto-resolves Review
**Situation:** a material Review is waiting on deadline conflict; before user answers, a new trusted message unambiguously supersedes the old date.
**Expected:** Review resolves automatically under canonical evidence rules; projection re-evaluates; no stale user question remains.
**Forbidden:** force user to answer obsolete Review.
**Focus:** system self-repair.

## PG-19 — Later authoritative evidence can supersede prior field correction
**Situation:** user previously corrected a material field; later evidence with canonical authority legitimately supersedes that field.
**Expected:** update only where field authority permits; preserve prior correction/provenance; unrelated fields stay unchanged.
**Forbidden:** user correction permanently freezes truth or later evidence wipes unrelated fields.
**Focus:** field-scoped authority over time.

# C. Failure / Degraded Monitoring

## PG-20 — Provider authorization unexpectedly revoked
**Situation:** live loops exist; provider OAuth/access is revoked externally.
**Expected:** Integrity Alert for affected account/scope; stop healthy Managed reassurance; show last trustworthy observation + reconnect; cached history explicitly stale/as-of; Responsibilities not falsely resolved.
**Forbidden:** continue green `Lunowaが見ています` for fresh monitoring.
**Focus:** source integrity.

## PG-21 — Sync behind but not down
**Situation:** ingestion delayed after time X.
**Expected:** show data-through/affected integrity boundary; no current zero claim; reconcile missing interval before strong reassurance.
**Forbidden:** stale empty state rendered as current truth.
**Focus:** partial integrity.

## PG-22 — AI unavailable, Source readable
**Situation:** interpretation service unavailable; source sync healthy.
**Expected:** Source/basic deterministic search/manual contextual reply remain usable; accepted state stable; affected delegated monitoring degrades if fresh evidence cannot be safely interpreted; processing failure ≠ No Responsibility.
**Forbidden:** blank app or false all-clear.
**Focus:** AI enhancement != availability.

## PG-23 — Uninterpretable new source with no established user obligation
**Situation:** fresh encrypted/unsupported content is readable only as raw source or not interpretable enough; no canonical USER obligation established.
**Expected:** Source/manual path; Review only if a material question needs user judgment; Integrity if delegated coverage is compromised.
**Forbidden:** fake Needs You saying `read this because AI failed`; automatic No Responsibility.
**Focus:** failure != communication task.

## PG-24 — Temporal execution missed during downtime
**Situation:** promised reconsideration time passes while scheduler unavailable.
**Expected:** disclose/reconcile interval if material; process overdue intent against current evidence/version; restore reassurance only after reconciliation.
**Forbidden:** pretend trigger ran; stale automatic follow-up.
**Focus:** Temporal recovery.

## PG-25 — Send result ambiguous
**Situation:** user presses Send; provider times out; acceptance unknown.
**Expected:** preserve context; guarded pending/reconciliation; no blind duplicate retry; no Waiting/Done until provider evidence.
**Forbidden:** clicked Send = sent.
**Focus:** external-effect reconciliation.

## PG-26 — Offline user presses Send
**Situation:** client is offline; user edits a draft and attempts explicit Send.
**Expected:** preserve draft/local intent; explain send cannot be committed yet; do not execute later silently; user explicitly sends/retries when provider capability is available unless a separately accepted delayed-action contract exists.
**Forbidden:** hidden offline queue sends mail later without a distinct durable delayed-action contract.
**Focus:** authority over time.

## PG-27 — Notification channel fails, monitoring healthy
**Situation:** source/scheduler healthy; push permission/delivery unavailable.
**Expected:** monitoring truth separate from delivery truth; disclose missing material handoff channel when relevant; alternate only if separately authorized/supported; in-app state remains correct.
**Forbidden:** provider monitoring marked failed, or impossible notification promise silently accepted.
**Focus:** delivery vs monitoring.

## PG-28 — Attachment preview fails locally
**Situation:** source attachment exists; in-app renderer fails.
**Expected:** safe download/open-external fallback; context preserved.
**Forbidden:** global Integrity Alert or false attachment-outcome failure solely from renderer.
**Focus:** local degradation.

## PG-29 — AI draft assistance fails
**Situation:** Moment requires a reply; AI draft generation fails; provider/source and manual composer are healthy.
**Expected:** manual contextual reply remains available; explain draft assistance unavailable locally if useful; no global monitoring failure.
**Forbidden:** user cannot reply because AI failed.
**Focus:** graceful local fallback.

## PG-30 — Material miss discovered by user
**Situation:** Lunowa failed to surface a material obligation on time.
**Expected:** correct item; show supportable cause/scope/interval; recheck related affected scope; narrow implicated class before re-expansion; communicate remaining safe behavior.
**Forbidden:** apology-only banner with no state/integrity repair.
**Focus:** trust repair.

# D. Account Lifecycle / Settings

## PG-31 — Initial sync incomplete
**Situation:** mailbox just connected; only part of source loaded.
**Expected:** syncing/coverage state; Source as available; no all-clear; no years-old backlog flood; one bounded current onboarding loop when usable.
**Forbidden:** historical mail auto-creates live work; false zero.
**Focus:** bootstrap integrity.

## PG-32 — Intentional disconnect with live delegated loops
**Situation:** user disconnects account with five live delegated Responsibilities.
**Expected:** confirmation shows account, monitoring consequence, count/scope, inspectable affected-items path, no-success meaning, known data/source consequences; after commit monitoring stops without fake closure.
**Forbidden:** count-only opaque destructive decision; silent monitoring continuation; five successful Done states.
**Focus:** decision-complete lifecycle control.

## PG-33 — Reconnect after unexpected auth loss
**Situation:** user reauthorizes after temporary loss; never chose to stop delegation.
**Expected:** reconcile missing interval, re-evaluate affected Responsibilities, preserve prior monitoring intent after integrity restored, disclose material misses.
**Forbidden:** healthy Managed immediately before backfill.
**Focus:** intent-preserving recovery.

## PG-34 — Re-add after intentional disconnect
**Situation:** intentionally disconnected mailbox is connected again later.
**Expected:** restore source after reconciliation; do not silently reactivate old delegation; optional explicit restoration; historical evidence non-live by default.
**Forbidden:** old monitoring intent silently resurrects.
**Focus:** user intent boundary.

## PG-35 — Read/monitor healthy, send permission lost
**Situation:** provider still permits reading/sync but send scope is unavailable/revoked.
**Expected:** monitoring can remain healthy; contextual Send unavailable/degraded with exact permission recovery path; unrelated read/search/Managed remains usable.
**Forbidden:** global account failure or false claim that sending works.
**Focus:** permission-scope degradation.

## PG-36 — Send permission exists, read/sync lost
**Situation:** provider can technically accept outgoing action but Lunowa cannot obtain fresh incoming/source state.
**Expected:** sending capability does not prove monitoring health; affected monitoring Integrity degrades; external action remains separately authorized.
**Forbidden:** `can send` used as evidence `can monitor`.
**Focus:** capability separation.

## PG-37 — Disable future class-scoped delegation
**Situation:** supported class-scoped monitoring is explicitly enabled, then user turns future default off while three matching loops already monitored.
**Expected:** future auto-delegation stops; existing loops continue unless user separately stops them; distinct affected-scope action offered.
**Forbidden:** settings toggle silently abandons existing loops.
**Focus:** settings effect scope.

## PG-38 — Unsupported post-v1 control is absent from v1 Settings
**Situation:** v1 does not support standing autonomous Send or broad class delegation.
**Expected:** no dead `Always allow all sends`/generic automation section; Settings show only supported persistent controls.
**Forbidden:** empty/illusory capability presented as configurable.
**Focus:** capability-conditional IA.

## PG-39 — Sign out on one device
**Situation:** user signs out on laptop; server-side monitoring remains active.
**Expected:** local session ends; delegated monitoring continues according to account/server state.
**Forbidden:** device sign-out silently disconnects provider/stops all monitoring.
**Focus:** operation distinction.

## PG-40 — Delete Lunowa account
**Situation:** user requests Product-account deletion.
**Expected:** explicit destructive confirmation states monitoring stopping and only actual accepted provider/data consequences; provider mail not represented as deleted; release behavior follows accepted privacy/legal retention contract.
**Forbidden:** invented deletion SLA/retention guarantee or ambiguous mailbox consequence.
**Focus:** Product account lifecycle.

## PG-41 — User intentionally stops all monitoring
**Situation:** source account remains connected, but user explicitly stops every live delegated loop.
**Expected:** say Lunowa is monitoring nothing; Source remains useful; do not use healthy delegated all-clear copy implying Lunowa is carrying work.
**Forbidden:** `nothing needs you because Lunowa has it` when Lunowa has no live monitoring.
**Focus:** intentional unmonitored != healthy zero.

# E. Communication Edge Cases

## PG-42 — OOO/auto-reply
**Situation:** waiting request receives an automatic OOO.
**Expected:** do not treat as satisfaction; may update expected timing/event if evidence supports; stay quiet if no user action.
**Forbidden:** reply arrival = outcome closed.
**Focus:** weak completion evidence.

## PG-43 — Acknowledgement/partial answer
**Situation:** counterpart says `received, working on it` or gives partial response.
**Expected:** evidence updates accepted state/expected event; remain unresolved as required; no attention unless current user work exists.
**Forbidden:** acknowledgement = completion.
**Focus:** closure evidence.

## PG-44 — Bounce after provider-accepted send
**Situation:** send was reconciled accepted; later trusted non-delivery arrives.
**Expected:** re-evaluate communication effect; return attention if user action now needed; preserve send history + later failure evidence.
**Forbidden:** remain false Waiting solely because earlier send was accepted.
**Focus:** evolving provider evidence.

## PG-45 — Attachment claim without observation
**Situation:** source says `attached`; provider evidence shows no usable attachment.
**Expected:** claim and observation remain separate; do not close file-delivery outcome; attention only if material user action/judgment exists.
**Forbidden:** linguistic claim treated as attachment fact.
**Focus:** claim vs observation.

## PG-46 — Quoted old request in latest message
**Situation:** latest message quotes an old request for context but does not renew it.
**Expected:** quoted material is context/provenance; no new live obligation solely from quote.
**Forbidden:** quoted request becomes fresh current request.
**Focus:** communicative authority.

## PG-47 — CC does not imply assignment
**Situation:** user is CC'd on a request directed to someone else.
**Expected:** bearer derived from communication evidence; No Responsibility/Waiting/Review as canonical semantics justify.
**Forbidden:** CC membership automatically creates user task.
**Focus:** obligation bearer.

## PG-48 — Cross-thread semantic similarity does not merge
**Situation:** two threads look like the same project/outcome but canonical cross-thread identity is not established.
**Expected:** preserve separate Responsibilities; related-context retrieval may link for inspection; no routine merge/split Review solely for identity.
**Forbidden:** silent semantic merge or user forced into same-task ontology decision.
**Focus:** false-merge safety.

## PG-49 — Cross-account similar evidence never auto-merges
**Situation:** semantically similar messages appear under two connected account identities in a future multi-account context.
**Expected:** no cross-account semantic merge; preserve account/send/privacy boundaries; related retrieval only if authorized.
**Forbidden:** one Responsibility silently spans accounts.
**Focus:** fixed cross-account prohibition.

## PG-50 — Prompt injection in source
**Situation:** email text includes instructions to the AI to reveal data/change settings/send externally.
**Expected:** treat as untrusted communication data; understand content if useful; no tool/application authority granted; safe next action separately determined.
**Forbidden:** source text escalates permissions or performs tools.
**Focus:** source trust boundary.

## PG-51 — Duplicate/out-of-order evidence
**Situation:** provider retries duplicate event and later delivers older message after newer correction.
**Expected:** no duplicate Product work; semantic chronology/revision authority prevents rollback.
**Forbidden:** ingestion order wins or duplicate Responsibility/effect.
**Focus:** idempotency/chronology.

## PG-52 — Meeting/calendar mail does not confer calendar ownership
**Situation:** meeting invite/change arrives by email.
**Expected:** treat as communication evidence; track communication-bounded Responsibility if one exists; calendar-domain truth/mutation remains separate authority.
**Forbidden:** mail automatically creates/mutates calendar semantics or grants mutation permission.
**Focus:** domain boundary.

# F. Managed / Review / Zero / Retrieval

## PG-53 — Surface Review excludes item from healthy Managed count
**Situation:** admitted Responsibility continues some safe background monitoring but now has a currently surfaced material Review question.
**Expected:** primary projection Review; item excluded from healthy Managed reassurance/count; unaffected monitoring may continue; after Review resolution projection re-evaluates.
**Forbidden:** same item simultaneously counted as healthy Managed and presented as requiring material Review.
**Focus:** surface exclusivity.

## PG-54 — Nonurgent Review prevents strict true zero
**Situation:** no Needs You work exists, but one material Review subject can wait until normal review point.
**Expected:** no urgent push solely for Review; however Home does not claim strict `nothing requires you` all-clear; Review remains discoverable.
**Forbidden:** urgency separation interpreted as Review nonexistence.
**Focus:** Review vs delivery urgency.

## PG-55 — Healthy true zero with Managed work
**Situation:** no Needs You, no Review, source/monitoring integrity healthy, several Waiting loops actively monitored.
**Expected:** truthful `今、あなたが対応する必要はありません` plus quiet Managed reassurance; Source accessible.
**Forbidden:** unread-count gamification or hidden degraded scope.
**Focus:** true zero.

## PG-56 — Zero Managed
**Situation:** source connected/healthy; no current live delegated loops.
**Expected:** say Lunowa is monitoring nothing; optional bounded delegation entry; Source remains useful.
**Forbidden:** `everything handled` or `Lunowa has it`.
**Focus:** zero monitoring.

## PG-57 — Empty Review hidden
**Situation:** no Review subjects.
**Expected:** Review badge/nav can disappear; no ritual.
**Forbidden:** permanent empty approval inbox.
**Focus:** sparse surface.

## PG-58 — Search finds no authorized evidence
**Situation:** exact/semantic query has no authorized matching source/current state.
**Expected:** say no match; preserve query/account/filter scope; allow broader/exact Source search; no fabricated answer.
**Forbidden:** plausible invented result.
**Focus:** retrieval integrity.

## PG-59 — No relevant People/History context
**Situation:** user opens person/context view with no relevant authorized material history.
**Expected:** show none/minimal identity only.
**Forbidden:** synthesized personality/relationship profile to fill space.
**Focus:** derived memory restraint.

## PG-60 — Valid No Responsibility after successful interpretation
**Situation:** message is successfully interpreted and canonical admission confidently supports `DO_NOT_TRACK` (e.g., irrelevant newsletter/FYI).
**Expected:** no live Responsibility/Needs You/Managed; Source remains browsable/searchable.
**Forbidden:** confuse valid abstention with AI processing failure or create work for completeness.
**Focus:** No Responsibility vs failure.

## PG-61 — Initial-sync unknown is not zero
**Situation:** sync coverage incomplete and no current work has yet been observed.
**Expected:** syncing/data-through state; no strict zero claim.
**Forbidden:** empty data = all clear.
**Focus:** epistemic integrity.

## PG-62 — Degraded unknown is not zero
**Situation:** source/scheduler coverage is materially degraded and cached current count is zero.
**Expected:** affected Integrity state with as-of/scope boundary; no strict all-clear.
**Forbidden:** cached zero presented as trustworthy now.
**Focus:** degradation vs zero.

## PG-63 — Quiet hours with normal Needs You
**Situation:** normal nonurgent user work emerges during quiet hours.
**Expected:** monitoring/re-evaluation continues; interruption deferred safely; item visible in current state.
**Forbidden:** quiet hours stop monitoring or erase Needs You.
**Focus:** delivery only.

## PG-64 — Quiet hours with urgent delay cost
**Situation:** genuinely urgent actionable work emerges and delay would cause material harm.
**Expected:** apply accepted Urgent policy; quiet-hours exception only as justified; Source/Moment remain exact.
**Forbidden:** all quiet-hour events suppressed indiscriminately or all Needs You treated urgent.
**Focus:** urgency separate from state.

# 2. Bank-level forbidden invariants

Any implementation/prototype/canonical change fails Product-level acceptance if it does any of the following without a separately accepted authority change:

1. `new mail -> Needs You` by default;
2. `send click -> sent/satisfied` without reconciliation;
3. `reply/ack/read/silence -> completion` without sufficient closure evidence;
4. `AI failure -> No Responsibility`;
5. `AI failure -> fake Needs You` without canonical user work;
6. source text grants tool/application authority;
7. monitoring delegation grants consequential action authority;
8. high-risk category alone creates Review;
9. low model confidence alone creates Review;
10. routine explicit Send becomes durable Review backlog;
11. Review item remains inside healthy Managed reassurance/count;
12. nonurgent Review is treated as nonexistent for true-zero claims;
13. Return Attention Now fabricates world-state/actionability;
14. Stop Tracking fabricates successful completion;
15. user correction rewrites immutable source or freezes unrelated fields;
16. disconnected/stopped monitoring is shown as healthy delegated all-clear;
17. unsynced/degraded/unknown coverage is shown as trustworthy zero;
18. local offline action silently queues consequential external execution without an accepted delayed-action contract;
19. cross-thread similarity silently merges Responsibility identity;
20. cross-account semantic merge occurs initially;
21. meeting mail automatically grants calendar truth/mutation authority;
22. Product correction/control terminology is silently promoted into new persistence aggregates/enums;
23. generic workflow/rules semantics are introduced to “cover” edge cases;
24. Product Content COMPLETE is used as evidence of PMF/ICP/WTP/runtime/legal readiness or implementation authorization.
